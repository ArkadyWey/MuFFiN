Contributing

If you would like to contribute to MuFFiN, please have a look at the guidelines below.

Workflow

We use Git and GitHub to coordinate our work. When making any kind of update, we try to follow the procedure below.

(a) Before you begin

  1. Create an issue where new proposals can be discussed before any coding is done.

  2. Create a branch from the dev branch of our repo (ideally on your own fork), where all changes will be made.

  3. Download the source code onto your local system, by cloning the repository (or your fork of the repository).

  4. Install MuFFiN with developer options.

You now have everything you need to start making changes!

(b) Writing your code

  1. MuFFiN is developed in Python, and makes heavy use of NumPy.

  2. Make sure to follow our coding style guidelines.

  3. Commit your changes to your branch with useful, descriptive commit messages: Remember these are publicly visible and should still make sense a few months ahead in time. While developing, you can keep using the GitHub issue you’re working on as a place for discussion. Refer to your commits when discussing specific lines of code.

  4. If you want to add a dependency on another library, or re-use code you found somewhere else, have a look at these guidelines.

(c) Merging your changes with MuFFiN

  1. Test your code!

  2. MuFFiN has online documentation at https://arkadywey.github.io/MuFFiN/. To make sure any new methods or classes you added show up there, please read the documentation section.

  3. If you added a major new feature, perhaps it should be showcased in an example notebook.

  4. When you feel your code is finished, create a pull request (PR) on MuFFiN’s GitHub page.

  5. Once a PR has been created, it will be reviewed by any member of the community. Changes might be suggested which you can make by simply adding new commits to the branch. When everything’s finished, someone with the right GitHub permissions will merge your changes into MuFFiN main repository.

Finally, if you really, really, really love developing MuFFiN, have a look at the current project infrastructure.

Coding style guidelines

MuFFiN follows the PEP8 recommendations for coding style. These are very common guidelines, and community tools have been developed to check how well projects implement them. We will soon use pre-commit hooks to check our code before committing it, and we recommend that you do the same.

Ruff

Use ruff to check your PEP8 adherence.

Naming

Naming is hard. We use CamelCase for class names, and start with an upper case letter. For example, MyOtherClass. Method and variable names are lower case, and use underscores for word separation. For example x or iteration_count.

Dependencies and reusing code

While it’s a bad idea for developers to “reinvent the wheel”, it’s important for users to get a reasonably sized download and an easy install. In addition, external libraries can sometimes cease to be supported, and when they contain bugs it might take a while before fixes become available as automatic downloads to MuFFiN users. For these reasons, all dependencies in MuFFiN should be thought about carefully, and discussed on GitHub.

Direct inclusion of code from other packages is possible, as long as their license permits it and is compatible with ours. Again, this should be considered carefully and discussed on Github. Snippets from blogs and stackoverflow can often be included without attribution, but if they solve a particularly nasty problem (or are very hard to read) it’s often a good idea to attribute (and document) them, by making a comment with a link in the source code.

Testing

We will use the unittest package for our tests. These will be implemented soon. These tests will typically just check that the code runs without error, and so, are more debugging than testing in a strict sense. Nevertheless, these will be essential to develop this codebase further.

Documentation

MuFFiN is documented in several ways.

First and foremost, every method and every class should have a docstring that describes in plain terms what it does, and what the expected input and output is, including type information.

We use the NumPy format (as opposed to Google, for example) by convention. The AutoDoctring tool in VSCode is a useful extension to simplify docstring writing.

We use Sphinx to convert the source documentation in MuFFiN/docs to HTML, PDF, and other formats. In particular, we use it to generate the documentation at https://arkadywey.github.io/MuFFiN/.

Building the documentation

To test and debug the documentation, it’s best to build it locally. To do this, navigate to your MuFFiN/docs directory in a console, and, in your terminal, run:

make html

You can then view a local version of the documentation in MuFFiN/docs/_build/html by clicking index.rst.

Example notebooks

Major MuFFiN features should be showcased in a similar way to our current examples, in Jupyter notebooks and stored in the MuFFiN/docs/_examples directory. Which features are “major” is of course wholly subjective, so please discuss on GitHub first.

All example notebooks should be listed in MuFFiN/docs/_examples/index.rst. Please follow the (naming and writing) style of existing notebooks and documentation files where possible.

Infrastructure

Continuous Integration using GitHub Actions

Each change pushed to the MuFFiN GitHub master branch will trigger the documentation to be automatically recompiled. In future, default actions may also include testing.

Configuration files for various GitHub actions workflow can be found in .github/worklfows.

Read the Docs

Documentation is built using Sphinx via ReadTheDocs and published on https://arkadywey.github.io/MuFFiN/index.html.
